# google-calendar-sync

複数の Google アカウントのカレンダーを **双方向** に同期し、予定の「時間枠」だけを設定した文言で埋める CLI ツールです。[Lynx](https://lynxcat.app/) のセルフホスト版にあたります。

元予定のタイトル・詳細・場所・参加者は**一切コピーしません**。同期先に作られるのは、時間だけが同じで中身が伏せられたブロック予定です。

```
┌─────────────┐
│ A カレンダー │  10/20 14:00-15:00「〇〇社と商談」
└──────┬──────┘
       │  時間枠のみ抽出（内容は捨てる）
       ├──────────────▶ B: 10/20 14:00-15:00「秘密の予定」
       └──────────────▶ C: 10/20 14:00-15:00「プライベートの予定」
```

参加カレンダーが3つなら **A→B, A→C, B→A, B→C, C→A, C→B の6方向すべて**を同期します。同期で作られた予定（ミラー）は同期元として扱わないため、ミラーがさらにミラーされて増殖することはありません。

## できること

- 異なる Google アカウント間の双方向・全対全同期
- 埋め込む文言を **方向ごとに個別設定**（A→B は「秘密の予定」、A→C は「プライベートの予定」など）
- 元予定の変更・削除に次回同期で追従（移動したら移動、消したら消える）
- 常に「今日から3ヶ月先」だけを同期（過去は同期しない）
- サービスアカウント / OAuth のどちらでも動作（構築をスクリプト化できるサービスアカウント方式を推奨）
- 画面で初期設定 → あとは15分間隔のバッチで同期し続ける
- 内容を一切コピーしないプライバシー設計

## 必要なもの

- Node.js 20 以上
- Google Cloud プロジェクト（無料枠で足ります）

## セットアップ

### 1. インストール

```bash
git clone https://github.com/Yamamoto-Shohei/google-calendar-sync.git
cd google-calendar-sync
npm install
npm link          # どこからでも `gcal-sync` で実行できるようにする（任意）
```

`npm link` を使わない場合は、以下すべての `gcal-sync` を `node /path/to/google-calendar-sync/src/cli.js` に読み替えてください。

### 2. Google Cloud 側の準備

Google カレンダーにプログラムから書き込む手段は OAuth しかなく、その資格情報を発行する窓口が Google Cloud だけなので、ここは避けられません。**費用はかからず（Calendar API は無料、カード登録も不要）、サーバーも立ちません。** 一度やれば使い回せます。

認証方式は2つあります。**ミラー予定の「作成者」を気にするなら OAuth、構築の手軽さを取るならサービスアカウント**です。

| | サービスアカウント | OAuth |
| --- | --- | --- |
| **ミラー予定の作成者** | `gcal-sync@....iam.gserviceaccount.com`（ロボットのアドレスが表示される） | **各アカウント自身** |
| 同意画面の設定・公開 | **不要** | 必要 |
| トークンの失効 | **しない** | 同意画面がテスト中だと**7日で失効** |
| 構築のコード化 | **スクリプト化できる** | 不可（Console 手作業、API が存在しない） |
| カレンダーの検出 | ID を手で指定 | 画面で自動検出 |
| ミラー用カレンダー | 手で作成して共有 | 自動作成 |
| 事前の手作業 | カレンダーごとに共有設定（1回） | アカウントごとに認可 |

どちらでも同期の動作は同じで、予定の所有権（`organizer`）はカレンダーの持ち主に残るため、いずれの場合も自分で編集・削除できます。違いは `creator` フィールドで、サービスアカウント方式だと予定の詳細にロボットのアドレスが出ます。

> サービスアカウントにユーザーを代理させて `creator` を各アカウントにする「ドメイン全体の委任」は、Google Workspace の管理者権限が必要で、そのドメイン内のアカウントにしか効きません。個人の @gmail.com アカウントでは使えません。

#### 方式 A: サービスアカウント

[gcloud CLI](https://cloud.google.com/sdk/docs/install) を入れて `gcloud auth login` したうえで、同梱スクリプトを実行します。

```bash
./scripts/setup-gcp.sh
```

プロジェクト作成・Calendar API 有効化・サービスアカウント作成・JSON 鍵の発行までを行います（冪等なので再実行可）。完了すると共有先アドレスが表示されます。

実行すると、**何をどのアカウントに作るかを表示して確認を求めます**。会社アカウントで `gcloud auth login` している状態だと、そのアカウント配下にプロジェクトが作られてしまうので、ここで確認してください（会社の組織ポリシーでプロジェクト作成が禁止されている場合もあります）。個人アカウントに切り替えるには `gcloud auth login` を実行してください。

| オプション | 用途 |
| --- | --- |
| `--yes` | 確認プロンプトを省略（CI など非対話実行で必要） |
| `--project-id ID` | 既存プロジェクトを使う／ID を指定する |
| `--key-out PATH` | 鍵の出力先を変える |
| `--sa-name NAME` | サービスアカウント名を変える |

そのあと、**同期したい各カレンダーをそのアドレスに共有**してください。ここだけは自動化できません（カレンダーの owner 権限が必要で、それを持つのは本人だけです）。

1. [calendar.google.com](https://calendar.google.com/) で左側のカレンダー名にホバー → ⋮ → 「設定と共有」
2. 「特定のユーザーまたはグループと共有する」→「ユーザーやグループを追加」
3. スクリプトが表示したアドレス（`gcal-sync@....iam.gserviceaccount.com`）を貼る
4. 権限は **「予定の変更権限」**（「すべての予定の詳細を表示」では書き込めません）

ミラー用カレンダーも、各アカウントで新規作成して同じく共有しておくのが推奨です（一括非表示とリセットができます）。

#### 方式 B: OAuth

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作成
2. 「API とサービス」→「ライブラリ」で **Google Calendar API** を有効化
3. 「API とサービス」→「OAuth 同意画面」を設定
   - User type は **外部（External）**
   - スコープに `https://www.googleapis.com/auth/calendar` を追加
   - 「テストユーザー」に**同期したい全アカウントのメールアドレス**を追加
4. 「API とサービス」→「認証情報」→「認証情報を作成」→「OAuth クライアント ID」
   - アプリケーションの種類は **デスクトップ アプリ**（リダイレクト URI の入力欄は出ません。ループバックは自動的に許可されます）
   - 作成後に表示される**クライアント ID とクライアント シークレット**を控える

認可時のリダイレクト先は `http://127.0.0.1:4765/oauth/callback` です（`GCAL_SYNC_PORT` で変更可、設定画面にも表示されます）。`localhost` ではなくループバック IP を使っているのは、`localhost` が `::1` に解決されると設定サーバー（`127.0.0.1` で待ち受け）に届かないためです。

もし認可時に `redirect_uri_mismatch` が出る場合は、「ウェブ アプリケーション」種別でクライアントを作り直し、承認済みのリダイレクト URI に上記 URL をそのまま登録してください。どちらの種別でもこのツールは動きます。

> **⚠️ 重要: 同意画面を「本番環境」に公開してください**
>
> OAuth 同意画面が「テスト中（Testing）」のままだと、**リフレッシュトークンが7日で失効**します。7日ごとに再認可が必要になり、バッチ同期が止まります。
>
> 「OAuth 同意画面」→「アプリを公開」→「本番環境に push」してください。自分専用の個人用途であれば、Google の審査は不要です（審査が必要になるのは、センシティブなスコープで多数の外部ユーザーに配布する場合です）。
>
> Google Workspace アカウントの場合は、User type を「内部（Internal）」にすれば、この制限はありません。
>
> この手順が煩わしい場合は方式 A を使ってください。

### 3. 画面で設定する

```bash
gcal-sync setup
```

`http://127.0.0.1:4765/?t=<ワンタイムトークン>` がブラウザで開きます（URL はターミナルにも表示されます）。画面に沿って上から埋めてください。

1. **認証方式** — サービスアカウント / OAuth を選ぶ
2. **鍵またはクライアント** — サービスアカウントなら JSON 鍵のパス、OAuth ならクライアント ID とシークレット
3. **Google アカウント**（OAuth のみ）— 「アカウントを追加」を同期したいアカウントの数だけ繰り返す
4. **同期するカレンダー** — 2つ以上追加すると自動的に全対全になる
   - サービスアカウント方式: 同期元とミラー先のカレンダー ID を入力（追加時に書き込み権限を検証します）
   - OAuth 方式: アカウントとカレンダーを選択（ミラー用サブカレンダーは自動作成）
5. **埋め込む文言** — 行が送信元・列が送信先のマトリクスで、各方向の文言を入力
6. **同期の設定** — 範囲（既定3ヶ月）・間隔（既定15分）・フィルタ
7. **実行とスケジュール** — 「アクセス確認」→「差分を確認」→「今すぐ同期」、最後に「定期実行を登録」

設定が済んだら Ctrl+C で画面を閉じてください。以降はバッチが動き続けます。

カレンダー ID は Google カレンダーの「設定と共有」→「カレンダーの統合」で確認できます。メインカレンダーならメールアドレスそのもの、サブカレンダーなら `...@group.calendar.google.com` 形式です。

#### ミラーの書き込み先について

カレンダー追加時に2つから選べます。

| | 専用サブカレンダー（既定・推奨） | 送信先の primary に直接 |
| --- | --- | --- |
| ミラーの置き場所 | 自動作成される `Synced (gcal-sync)` | 送信先の primary |
| 一括で非表示にできる | **できる**（カレンダーのチェックを外す） | できない |
| 完全リセット | **カレンダーごと削除で済む** | ツール経由で消す必要がある |
| 実予定との区別 | カレンダーの色で分かれる | グレーの色分けのみ |
| ループ防止 | 構造 + マーカーの二重 | マーカーのみ |

どちらでも同期は正しく動きます。迷ったら既定のままにしてください。

## コマンド

```bash
gcal-sync setup                 # 設定画面を開く
gcal-sync sync                  # 同期を1回実行（バッチが叩く本体）
gcal-sync sync --dry-run        # 何も書き込まず、差分だけ表示
gcal-sync sync --only 'A->B'    # 1方向だけ実行（`>` がリダイレクトになるのでクォート必須）
gcal-sync sync --only A         # A に関わる4方向だけ実行
gcal-sync sync --json           # 実行結果を JSON で出力
gcal-sync status                # 設定・認可状態・スケジュール・前回実行を表示
gcal-sync doctor                # 全カレンダーに必要な権限でアクセスできるか確認
gcal-sync install-cron          # 定期実行を登録（macOS は launchd、他は crontab）
gcal-sync uninstall-cron        # 定期実行を解除
```

`doctor` は、同期元に読み取り権限・ミラー先に書き込み権限があるかを1件ずつ検証します。サービスアカウント方式では共有設定の漏れがそのまま同期失敗になるので、スケジュール登録前に実行してください。

終了コード: `0` 成功 / `1` 一部失敗 / `2` 設定不正・未認可。

## 仕組み

### 同期状態は予定自体に持つ

ローカル DB は持ちません。ミラー予定の `extendedProperties.private` に以下を埋め込み、毎回それを突き合わせます。

| キー | 内容 |
| --- | --- |
| `gcsMirror` | 固定値 `1`。**「これはツールが作ったミラーだ」という印** |
| `gcsPair` | 方向 ID（`A->B` など） |
| `gcsSourceEventId` | 元予定の ID |
| `gcsFingerprint` | 書き込んだ内容のハッシュ |

`extendedProperties` は Google カレンダーの UI に表示されず、ユーザーが触れないため、ID が失われて迷子のミラーが生まれることがありません。

この方式の利点は、**設定ファイルを失っても別マシンに移しても、既存のミラーをそのまま引き継げる**ことです。状態が実際のカレンダーと乖離しません。

### 1回の同期でやること

1. ウィンドウを決める（今日 00:00 〜 3ヶ月後）
2. 各カレンダーの予定を取得（`singleEvents=true` で繰り返し予定を実体に展開）。このとき **`gcsMirror` を持つ予定を除外**する ← ループ防止の中核
3. 各ミラー置き場から、マーカー付きの予定だけを取得
4. 方向ごとに突き合わせて、作成 / 更新 / 削除を適用

`gcsFingerprint` には「書き込んだ内容すべて」のハッシュが入ります。予定の時間が動いたときだけでなく、**画面で文言を変更したときも**次回同期で既存ミラー全件が更新されます。

ミラーを同期元から除外するので、方向の処理順は結果に影響しません。何度流しても同じ状態に収束します（冪等）。

### 削除の安全弁

双方向同期では「元に無い → 削除」が暴走すると被害が大きいため、4重に歯止めをかけています。

- **`gcsMirror` を持たない予定は絶対に削除しない** — 手で作った予定は消えません
- **同期元の取得に失敗した方向は丸ごとスキップ** — トークン失効を「予定ゼロ」と誤認してミラーを全消しする事故を防ぎます
- **同期元が0件なのにミラーがある場合は削除せず警告** — 本当に全部消したときは `--allow-empty-source` を付けます
- **1回・1方向あたりの削除件数に上限**（既定100件）— 超えたら中断して警告

### 過去の予定について

ウィンドウは常に「今日から先」です。ミラーは作られた位置に残り、日付が過ぎると単にウィンドウの外に出て、以後は触られません（履歴として残ります）。

## 設定ファイル

`~/.google-calendar-sync/`（ディレクトリは `0700`、ファイルは `0600`）

| ファイル | 内容 | 秘密情報 |
| --- | --- | --- |
| `config.json` | アカウント・カレンダー・文言・フィルタ | 含まない |
| `tokens.json` | リフレッシュトークン（OAuth 方式） | **含む** |
| `client.json` | OAuth クライアント ID / シークレット | **含む** |
| `service-account.json` | サービスアカウントの秘密鍵 | **含む** |
| `last-run.json` | 前回実行の結果 | 含まない |
| `sync.log` | バッチ実行のログ | 含まない |

`config.json` には秘密情報が入らない（メールアドレス・カレンダー ID・文言のみ）ので、リポジトリで管理できます。秘密情報は上記の別ファイルに分離してあり、`.gitignore` 済みです。

`GCAL_SYNC_HOME` 環境変数で場所を変えられます（独立した複数のメッシュを運用する場合など）。

通常は画面から編集しますが、直接書いても構いません。

サービスアカウント方式では `accounts` が空になり、カレンダーは実 ID で指定します（`"primary"` はサービスアカウント自身の空のカレンダーを指してしまうため、エラーになります）。

```json
{
  "version": 1,
  "auth": {
    "mode": "service-account",
    "keyFile": "~/.google-calendar-sync/service-account.json"
  },
  "accounts": [],
  "members": [
    {
      "id": "A",
      "label": "仕事",
      "sourceCalendarId": "a@example.com",
      "writeMode": "subcalendar",
      "mirrorCalendarId": "xxxx@group.calendar.google.com",
      "enabled": true
    }
  ]
}
```

OAuth 方式の全体例:

```json
{
  "version": 1,
  "auth": { "mode": "oauth" },
  "window": { "futureMonths": 3 },
  "syncIntervalMinutes": 15,
  "defaultLabel": "予定あり",
  "accounts": [
    { "id": "acct-a", "email": "a@example.com" },
    { "id": "acct-b", "email": "b@example.com" }
  ],
  "members": [
    {
      "id": "A",
      "label": "仕事",
      "accountId": "acct-a",
      "sourceCalendarId": "primary",
      "writeMode": "subcalendar",
      "mirrorCalendarId": "xxxx@group.calendar.google.com",
      "enabled": true
    },
    {
      "id": "B",
      "label": "プライベート",
      "accountId": "acct-b",
      "sourceCalendarId": "primary",
      "writeMode": "subcalendar",
      "mirrorCalendarId": "yyyy@group.calendar.google.com",
      "enabled": true
    }
  ],
  "labels": {
    "A->B": "秘密の予定",
    "B->A": "プライベートの予定"
  },
  "filters": {
    "skipAllDay": false,
    "skipDeclined": true,
    "skipTransparent": true,
    "skipWorkingLocation": true,
    "minDurationMinutes": 0
  },
  "visibility": "private",
  "reminders": "none",
  "annotateDescription": true,
  "mirrorColorId": "8",
  "safety": { "maxDeletesPerPairPerRun": 100 }
}
```

### 文言の差し込みトークン

固定文字列のほか、以下が使えます。

| トークン | 展開結果 |
| --- | --- |
| `{summary}` | 元予定のタイトル（※内容が同期先に出ます） |
| `{start}` / `{end}` | `2026-10-20 14:00` 形式 |
| `{durationMinutes}` | `90` |
| `{calendarName}` | 送信元カレンダーの名前（例「仕事」） |

例: `{calendarName}の予定` → `仕事の予定`

### フィルタ

| 設定 | 既定 | 動作 |
| --- | --- | --- |
| `skipDeclined` | `true` | 自分が辞退した予定を同期しない |
| `skipTransparent` | `true` | 「空き時間」扱いの予定を同期しない |
| `skipAllDay` | `false` | 終日予定を同期しない |
| `skipWorkingLocation` | `true` | 勤務場所（在宅／出社）の登録を同期しない |
| `minDurationMinutes` | `0` | この分数未満の予定を同期しない |

フィルタを後から有効にすると、対象外になった予定のミラーは次回同期で削除されます。

## プライバシー

ミラーにコピーされるのは **開始時刻・終了時刻・終日フラグ** だけです。

- タイトルは設定した文言に置き換わります（`{summary}` を使った場合を除く）
- 詳細・場所・参加者・会議 URL・添付ファイルはコピーされません
- ミラーは `visibility: private`、通知オフで作成されます
- 参加者を付けないので、ミラー作成で第三者に招待メールが飛ぶことはありません
- 認可情報はローカルの `0600` ファイルにのみ保存され、外部に送信されません

## トラブルシューティング

まずは `gcal-sync doctor` を実行してください。カレンダーごとに必要な権限があるかを個別に表示します。

**サービスアカウント方式で「アクセスできない」と出る**
そのカレンダーの共有設定にサービスアカウントのアドレスが入っていません。`gcal-sync status` でアドレスを確認し、カレンダーの「設定と共有」で追加してください。権限は「予定の変更権限」が必要です（「すべての予定の詳細を表示」だと読めても書けません）。

**サービスアカウント方式で同期が0件になる**
`sourceCalendarId` が `"primary"` になっていないか確認してください。サービスアカウントにとっての `primary` は自分自身の空のカレンダーです。実際のカレンダー ID（メールアドレスまたは `...@group.calendar.google.com`）を指定してください。現在はバリデーションで弾きますが、古い設定ファイルでは起こりえます。

**`setup-gcp.sh` が「credentials have expired」と言う**
`gcloud auth list` でアカウントが ACTIVE に見えていても、トークンが失効していることがあります。`gcloud auth login` で再認証してください。

**`setup-gcp.sh` がプロジェクトを作れない**
会社／Workspace アカウントは、組織外にプロジェクトを作成できないことがあります。既存プロジェクトを `--project-id` で指定するか、`gcloud auth login` で個人アカウントに切り替えてください。

**秘密鍵が読めないというエラー**
鍵ファイルが途中で切れているか、再エンコードされています。Google Cloud で新しい鍵を発行してください（`./scripts/setup-gcp.sh` は既存の鍵があれば残すので、ローテートする場合は先にファイルを消してください）。

**`invalid_grant` / 7日でトークンが切れる**
OAuth 同意画面が「テスト中」のままです。「本番環境に push」してから `gcal-sync setup` で再認可してください。この問題を根本的に避けたい場合は、サービスアカウント方式に切り替えてください。

**リフレッシュトークンが返ってこない**
そのアカウントで以前に認可済みの場合に起きます。[アカウントのアクセス権](https://myaccount.google.com/permissions)から当該アプリを削除して、もう一度認可してください。

**ミラーが増殖している**
`gcal-sync status` で、ある member の `sourceCalendarId` が他の member の `mirrorCalendarId` と一致していないか確認してください（警告が出ます）。本来は `gcsMirror` マーカーで防がれる状況です。

**ミラーが削除されない / 警告が出る**
安全弁が働いています。`gcal-sync sync --dry-run` で削除対象を確認し、意図どおりなら `--allow-empty-source` を付けるか、`safety.maxDeletesPerPairPerRun` を上げてください。

**バッチが動いていない**
`gcal-sync status` でスケジュールの状態を確認し、`~/.google-calendar-sync/sync.log` を見てください。macOS では `launchctl print gui/$UID/com.googlecalendarsync.sync` でも確認できます。

**全部やり直したい**
サブカレンダー構成なら、Google カレンダーで `Synced (gcal-sync)` カレンダーを削除し、`gcal-sync setup` で組み直してください。
